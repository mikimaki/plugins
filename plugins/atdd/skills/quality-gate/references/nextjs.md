# Quality gate setup: Next.js (React, Prisma, MySQL)

Set `"stack": "nextjs"` for a Next.js app (App Router). It builds on the TypeScript setup in `typescript.md`. The differences:
- the acceptance tests run in a real browser against the production build, through playwright-bdd;
- unit and component tests run in Vitest;
- coverage comes from three places at once: Vitest, the Next.js server and Chromium.

Templates are in `${CLAUDE_SKILL_DIR}/templates/nextjs/`, plus four scripts from `templates/typescript/`.

These versions were verified end-to-end in October 2026 on a sample App Router app with a server action, a route handler, React Server and Client Components and a Prisma model:
- Node 22, Next.js 16.4 (Turbopack), React 19.3, TypeScript 6.0;
- Prisma 7.10 (`prisma-client` generator, `@prisma/adapter-mariadb`), MySQL 8;
- Playwright 1.63 with playwright-bdd 9.2;
- Vitest 5.0 with React Testing Library 16 and jsdom;
- StrykerJS 10.1;
- ESLint 10 with eslint-config-next 16.4 and sonarjs 4.2;
- monocart-coverage-reports 3.2, dependency-cruiser 18.7, knip 6.44 and jscpd 5.4.2.

One part didn't run for real: Prisma's schema engine (`prisma migrate`) couldn't be downloaded in the verification sandbox, so a stand-in applied the same migration SQL.

## Prerequisites

- **Node 22+** and **TypeScript 6.0.x**, as for TypeScript.
- **MySQL 8 for the tests.** The tests use a database of their own, never the development one:
  - `TEST_DATABASE_URL`, or the default in `test/test-database.ts`;
  - its name must end in `_test`. Each Stryker worker adds `_w<n>`.
  - Every test run resets it with `prisma migrate reset --force`, so the MySQL user needs the rights to create and drop those databases.
- **Python 3.9+** for `gate.py`, plus lizard and diff-cover: `pipx install lizard==1.24.3 && pipx install diff-cover`.
- **Chromium for Playwright:** `npx playwright install chromium`.

## Dev dependencies

```bash
npm i -D @playwright/test playwright-bdd vitest @vitest/coverage-v8 @vitejs/plugin-react jsdom \
  @testing-library/react @testing-library/dom @testing-library/user-event \
  monocart-coverage-reports vitest-monocart-coverage \
  @stryker-mutator/core @stryker-mutator/vitest-runner @stryker-mutator/typescript-checker \
  eslint eslint-config-next typescript-eslint eslint-plugin-sonarjs dependency-cruiser knip prettier dotenv
npm i server-only
```

- Keep `@vitest/coverage-v8` on the same version as `vitest`.
- Prisma (`prisma`, `@prisma/client` and the MySQL/MariaDB driver adapter) is the app's own dependency. Keep its client generated by `prisma generate` (a `postinstall` script does it on install); the gate's build check runs it too.
- The Prisma client's output folder (e.g. `src/generated/prisma`) is generated code: the gate, ESLint, Stryker, knip and dependency-cruiser all skip `src/generated/`. Git-ignore it.

## How the gate drives the tools

Everything in `typescript.md` applies, with these differences:

- **Build:** `npx prisma generate && npx tsc --noEmit` when the repo depends on Prisma.
- **Tests (full mode):** the gate sets `ATDD_COVERAGE_DIR` and runs `commands.unitTests`, then `commands.acceptanceTests`:
  - Vitest records through vitest-monocart-coverage.
  - Playwright builds the app with `ATDD_COVERAGE=1`, which turns on the source maps in `next.config.ts`. It then starts `next start` with `NODE_V8_COVERAGE`, so the server records its coverage when Playwright stops it.
  - The `recordBrowserCoverage` fixture records Chromium's coverage of every page and maps it back through the build's source maps.
  - `node scripts/atdd/coverage.mjs merge` merges all three. A line or branch is covered when a unit test, the server or the browser ran it.
- **Undefined steps:** `npx bddgen`, which fails on a step without a definition.
- **Mutation:** StrykerJS runs the Vitest tests only: the acceptance tests need a production build per mutant, which takes far too long. So every rule needs a unit test that pins it, not just a scenario. Each Stryker worker uses its own test database.
- **Vulnerabilities:** `npm audit --omit=dev --audit-level=high`, or `pnpm audit --prod --audit-level high` when the repo has `pnpm-lock.yaml`.

A full run builds the app and runs the browser tests, so expect several minutes; mutation testing adds more.

## What 100% coverage asks of a Next.js app

- **Every changed line and branch must run in some test.** Code that only runs in one environment, such as `if (process.env.NODE_ENV !== 'production')` around the Prisma client cache, can never be covered by tests that run the production build. Write it without the branch (`globalThis.prisma ??= new PrismaClient(…)` works in every environment), or keep it out of `src/`.
- **V8 counts branches as code that runs only sometimes:** either side of `?:`, the right of `&&`/`||`/`??`, a `case`, an `if`'s body. An `if` without `else` is covered once its body ran.
- **Browser coverage of a page is lost when the app itself loads another document:** a plain `<a>` to another page, or `window.location`. Navigation through `next/link`, the router or `page.goto` keeps it. When a branch that only the browser runs shows up as uncovered, check whether a full-page load hides it, and use `<Link>` where the app should navigate client-side anyway.
- **Server-only code** (`import 'server-only'`, Prisma queries, server actions) is covered by the server's coverage and by Vitest tests that call it directly; `vitest.setup.ts` mocks `server-only` for that.
